# Requirements Document — Domain Events Model

> **Technology-agnostic spec.** References **Technology Roles** from
> `01-initial-setup/01-technology-stack`. Contains no product names or versions.

## Introduction

This feature defines the **complete domain event schema catalogue** for the
platform's `EVENT_STREAM`. It specifies every event type emitted across the
trade lifecycle — from initial capture through settlement, plus amendment,
cancellation, risk completion, EOD status, and replay/reprocessing signals.
Every event schema defined here is the contract between the producing bounded
context and all consuming bounded contexts; changes to a schema are breaking
changes governed by the `SchemaRegistry` compatibility rules in
`03-events/01-kafka-topic-design`.

All domain event types are sourced from the `shared-domain-contracts` shared
kernel (`02-microservices/01-shared-domain-contracts`). This spec defines
the **field-level contracts** for each event type; the shared kernel provides
the corresponding `SERVICE_LANGUAGE` types. All identifiers in examples use
the synthetic `FX-` prefix. All organization and service names are fictional.

---

## Glossary

- **DomainEvent**: An immutable record of something that happened in a bounded
  context, published to the `EVENT_STREAM`; never updated or deleted after
  publication.
- **EventEnvelope**: The outer wrapper carried by every `DomainEvent` on the
  `EVENT_STREAM`, containing metadata common to all events.
- **EventPayload**: The inner, event-type-specific fields carried inside an
  `EventEnvelope`.
- **TradeLifecycleEvent**: A `DomainEvent` describing a state change in the
  trade lifecycle (e.g. `TradeCaptured`, `TradeValidated`, … `TradeSettled`).
- **TradeAmendedEvent**: A `DomainEvent` describing a material field change to
  an existing trade.
- **TradeCancelledEvent**: A `DomainEvent` describing the cancellation of an
  existing trade.
- **RiskCalculationRequestedEvent**: A `DomainEvent` requesting risk computation
  for a trade.
- **RiskCalculationCompletedEvent**: A `DomainEvent` announcing the completed
  risk result for a trade.
- **RiskCalculationFailedEvent**: A `DomainEvent` announcing that risk
  computation could not be completed.
- **EODStatusEvent**: A `DomainEvent` describing a regional or global EOD
  processing state change.
- **ReplayRequestedEvent**: A `DomainEvent` requesting that a trade's event
  history be replayed from a specified point; used by recovery workflows only.
- **EventId**: A UUID that uniquely identifies a single `DomainEvent` instance;
  used for idempotent consumption (GP-Rq-5).
- **CorrelationId**: The UUID propagated across all events, logs, and API calls
  for a single logical request (GP-Rq-2).
- **SourceService**: The `spring.application.name` of the `Service_Module` that
  published the event.
- **OccurredAt**: The ISO-8601 instant at which the domain fact occurred
  (business time, not publish time).
- **SchemaVersion**: The integer version of the event schema as registered in
  the `SchemaRegistry`.

## Requirements

### Requirement 1: Event Envelope (Common Metadata)

**User Story:** As an event consumer, I want every event to carry a standard
set of metadata fields regardless of event type, so that I can implement
correlation, deduplication, and routing once and apply it to all events.

#### Acceptance Criteria

1. EVERY `DomainEvent` published to the `EVENT_STREAM` SHALL carry an
   `EventEnvelope` containing at minimum: `eventId` (UUID), `eventType`
   (string matching the `TradeEventType` enum), `schemaVersion` (integer),
   `correlationId` (UUID), `tradeId` (string, `FX-` prefixed), `sourceService`
   (string), `occurredAt` (ISO-8601 instant), and `publishedAt` (ISO-8601
   instant, the actual broker publish time).
2. THE `eventId` SHALL be generated by the producing service and SHALL be unique
   across all events on the platform; consumers SHALL use `eventId` as the
   idempotency key (per GP-Rq-5).
3. THE `correlationId` SHALL be propagated from the inbound request or upstream
   event that triggered this event (per GP-Rq-2); it SHALL NOT be a new UUID
   generated at publish time unless no upstream correlation context exists.
4. THE `occurredAt` field SHALL represent the business instant (e.g. when the
   trade state changed), not when the message was written to the broker;
   `publishedAt` captures broker write time separately.
5. THE `schemaVersion` SHALL match the version registered in the `SchemaRegistry`
   for the corresponding `SchemaSubject`; a consumer that cannot handle the
   received `schemaVersion` SHALL route the message to the `DLQ`.
6. EVERY `EventEnvelope` field SHALL be non-null; an event with a null or blank
   required envelope field SHALL be treated as malformed and routed to the `DLQ`.

### Requirement 2: Trade Lifecycle Events

**User Story:** As a consuming bounded context, I want a well-defined event
for each trade lifecycle state transition so that I can react to exactly the
transitions I care about without parsing free-text status fields.

#### Acceptance Criteria

1. THE following `TradeLifecycleEvent` types SHALL be defined, each carrying the
   `EventEnvelope` plus the `EventPayload` fields listed:

   | EventType | Required PayloadFields |
   |---|---|
   | `TRADE_CAPTURED` | `tradeId`, `currencyPair` (base, quote, pairCode), `notionalAmount`, `notionalCurrency`, `direction`, `tradeDate`, `valueDate`, `counterpartyId`, `tradingBookId`, `regionCode` |
   | `TRADE_VALIDATED` | `tradeId`, `validatedAt` |
   | `TRADE_ENRICHED` | `tradeId`, `enrichedAt`, `marketDataSnapshotId` |
   | `TRADE_RISK_CALCULATED` | `tradeId`, `calculationId`, `riskAmount`, `riskCurrency`, `riskLevel`, `ruleVersion` |
   | `TRADE_BOOKED` | `tradeId`, `bookedAt`, `bookingDate`, `regionCode` |
   | `TRADE_ALLOCATED` | `tradeId`, `allocatedAt` |
   | `TRADE_CONFIRMED` | `tradeId`, `confirmedAt`, `counterpartyId` |
   | `TRADE_SETTLED` | `tradeId`, `settledAt`, `settlementDate`, `nostroAccount` (synthetic) |
   | `TRADE_FAILED` | `tradeId`, `failedAt`, `failureReason`, `failedStage` |

2. EACH `TradeLifecycleEvent` payload SHALL carry only fields that are known
   to the producing bounded context at the time of the state change; fields
   unknown at that stage SHALL be omitted rather than null-filled.
3. THE `TRADE_CAPTURED` event SHALL carry the complete trade fields as captured
   at ingestion because it is the first event for a trade and downstream
   consumers rely on it to bootstrap their own state.
4. MONETARY fields in event payloads (e.g. `notionalAmount`, `riskAmount`) SHALL
   be represented as JSON numbers with a fixed decimal scale, consistent with
   the `SERIALIZATION` role's monetary value convention.
5. DATE and INSTANT fields SHALL be represented as ISO-8601 strings per the
   `SERIALIZATION` role.

### Requirement 3: Trade Amendment and Cancellation Events

**User Story:** As a downstream bounded context, I want explicit amendment and
cancellation events carrying the changed fields so that I can update my local
projection without re-fetching the full trade.

#### Acceptance Criteria

1. THE `TRADE_AMENDED` event SHALL carry: `tradeId`, `amendedAt`, `amendedBy`
   (synthetic service name), `amendedFields` (array of
   `{fieldName, previousValue, newValue}`), and `amendmentReason` (free text,
   no real data).
2. THE `TRADE_CANCELLED` event SHALL carry: `tradeId`, `cancelledAt`,
   `cancelledBy` (synthetic service name), and `cancellationReason`.
3. WHEN a `TRADE_AMENDED` event is published, ALL fields that changed SHALL be
   listed in `amendedFields`; fields that did not change SHALL NOT appear.
4. THE `TRADE_CANCELLED` event SHALL be the terminal lifecycle event for a
   cancelled trade; no further lifecycle events SHALL be published for a
   cancelled `tradeId`.
5. BOTH event types SHALL carry the full `EventEnvelope` (Requirement 1) with
   the same `tradeId` as the original `TRADE_CAPTURED` event.

### Requirement 4: Risk Events

**User Story:** As the trade lifecycle and EOD processing contexts, I want
explicit risk request and result events so that risk computation is decoupled
from trade capture and can be replayed independently.

#### Acceptance Criteria

1. THE `RISK_CALCULATION_REQUESTED` event SHALL carry: `tradeId`,
   `calculationRequestId` (UUID), `currencyPair`, `notionalAmount`,
   `notionalCurrency`, `regionCode`, `tradingBookId`, `marketDataSnapshotId`,
   and `requestedAt`.
2. THE `RISK_CALCULATION_COMPLETED` event SHALL carry: `tradeId`,
   `calculationId`, `calculationRequestId` (matching the request),
   `riskAmount`, `riskCurrency`, `riskLevel`, `contributingFactors` (array of
   `{factorName, contribution, currency}`), `ruleVersion`, `rulesFired`
   (array of rule identifiers, synthetic), and `calculatedAt`.
3. THE `RISK_CALCULATION_FAILED` event SHALL carry: `tradeId`,
   `calculationRequestId`, `failureReason`, and `failedAt`.
4. THE `calculationRequestId` SHALL link a `RISK_CALCULATION_COMPLETED` or
   `RISK_CALCULATION_FAILED` event back to its originating
   `RISK_CALCULATION_REQUESTED` event; consumers SHALL use this to correlate
   asynchronous request/response pairs.
5. CONTRIBUTING factors in `RISK_CALCULATION_COMPLETED` SHALL sum to the
   `riskAmount` within the platform's defined rounding tolerance.

---

### Requirement 5: EOD Status Events

**User Story:** As the EOD readiness agent and downstream consumers, I want
structured EOD status events so that regional and global close progress is
observable on the event stream without polling REST APIs.

#### Acceptance Criteria

1. THE following EOD status event types SHALL be defined:

   | EventType | Required PayloadFields |
   |---|---|
   | `REGIONAL_CLOSE_STARTED` | `regionCode`, `globalBusinessDate`, `startedAt` |
   | `REGIONAL_CLOSE_READY` | `regionCode`, `globalBusinessDate`, `readyAt`, `branchCount`, `completedBranchCount` |
   | `REGIONAL_CLOSE_BLOCKED` | `regionCode`, `globalBusinessDate`, `blockedAt`, `blockerCode`, `blockerDescription` |
   | `REGIONAL_CLOSE_CLOSED` | `regionCode`, `globalBusinessDate`, `closedAt` |
   | `GLOBAL_CONSOLIDATION_COMPLETED` | `globalBusinessDate`, `consolidatedAt`, `regionSummary` (array of `{regionCode, status}`) |

2. THE `PartitionKey` for all EOD status events SHALL be `regionCode` (per
   `03-events/01-kafka-topic-design` Requirement 2).
3. THE `globalBusinessDate` field SHALL be an ISO-8601 date string
   (`YYYY-MM-DD`) representing the business date being closed, not the
   wall-clock date of the event.
4. THE `GLOBAL_CONSOLIDATION_COMPLETED` event SHALL be published exactly once
   per `globalBusinessDate`; re-publishing this event for an already-completed
   date SHALL be treated as a duplicate (idempotent by `globalBusinessDate`).

---

### Requirement 6: Replay and Reprocessing Events

**User Story:** As a recovery workflow, I want a structured replay-requested
event so that reprocessing is triggered through the event stream rather than
by direct service calls, keeping the audit trail intact.

#### Acceptance Criteria

1. THE `REPLAY_REQUESTED` event SHALL carry: `tradeId`, `replayFromEventType`
   (the `TradeEventType` from which replay should restart), `requestedBy`
   (synthetic service or agent name), `requestedAt`, and `approvalReference`
   (the human-approval reference from the HITL gate).
2. THE `approvalReference` field SHALL be non-null; a `REPLAY_REQUESTED` event
   without a valid `approvalReference` SHALL be treated as unauthorized and
   routed to the `DLQ` by the consuming service.
3. THE `REPLAY_REQUESTED` event SHALL be published only by the
   `state-reconciliation-service` or a gated recovery workflow; no other
   service SHALL produce this event type.
4. CONSUMERS of `REPLAY_REQUESTED` SHALL treat it as a medium-risk action
   (per the platform action-gate pattern) and SHALL verify the
   `approvalReference` before executing replay.

---

### Requirement 7: Schema Catalogue and Documentation

**User Story:** As a developer integrating with the event stream, I want a
single catalogue document that lists every event type, its topic, its
`SchemaSubject`, and its field list, so that I can implement producers and
consumers without hunting across multiple specs.

#### Acceptance Criteria

1. THE spec folder `03-events/02-domain-events-model/` SHALL contain a
   `schema-catalogue.md` that lists every event type defined in Requirements
   2–6, its target topic (per `03-events/01-kafka-topic-design`), its
   `SchemaSubject`, its `PartitionKey`, and all required payload fields with
   their types and descriptions.
2. EVERY field in the schema catalogue SHALL carry a description stating its
   business meaning, not just its data type.
3. WHEN a new event type is added to the platform, the `schema-catalogue.md`
   SHALL be updated in the same pull request as the producing service's spec.
4. ALL example values in the schema catalogue SHALL use `Synthetic_Identifier`s
   (`FX-` prefixed trade IDs, fictional service names, fictional rule IDs).
