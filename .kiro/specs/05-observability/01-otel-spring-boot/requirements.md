# Requirements Document — OTel Spring Boot Instrumentation

> **Technology-agnostic spec.** References **Technology Roles** from
> `01-initial-setup/01-technology-stack`. Contains no product names or versions.

## Introduction

This feature defines the **OpenTelemetry instrumentation standard** for all
`SERVICE_FRAMEWORK` microservices in `Middleware/`. It covers auto-instrumentation
configuration, span naming conventions, W3C TraceContext propagation, and
business-context baggage (`tradeId`, `regionCode`, `correlationId`). This spec
adds **no new business logic** — it instruments the services built in phase 02.

Every requirement here complements the observability golden-path item
`architecture-golden-path/01-service-nfrs` GP-Rq-8, which mandates that every
service emit traces, metrics, and logs. This spec defines *how* tracing is
configured in detail; GP-Rq-8 defines *that* it must exist. All identifiers
in examples use the synthetic `FX-` prefix.

---

## Glossary

- **OTelAgent**: The `OBSERVABILITY_TRACING` auto-instrumentation agent attached
  to the JVM at startup; captures HTTP, database, and messaging spans
  automatically without code changes.
- **Span**: A single named unit of work within a distributed trace; has a
  start time, end time, status, and attributes.
- **Trace**: The directed acyclic graph of `Span`s representing a complete
  end-to-end operation across one or more services.
- **TraceContext**: The W3C standard headers (`traceparent`, `tracestate`) that
  propagate `Trace` identity across HTTP and messaging boundaries.
- **Baggage**: Key-value pairs propagated alongside `TraceContext` that carry
  business context (e.g. `tradeId`, `regionCode`) for downstream enrichment.
- **SpanName**: The human-readable identifier for a `Span`; follows the
  convention `{service-name}/{operation-type}/{entity}`.
- **ServiceName**: The `OBSERVABILITY_TRACING` resource attribute
  `service.name`, set to the service's `spring.application.name`.
- **OTelCollector**: The `OBSERVABILITY_TRACING` collector/exporter that
  receives spans from all services and forwards them to the tracing backend.

## Requirements

### Requirement 1: Auto-Instrumentation Configuration

**User Story:** As a platform operator, I want every `SERVICE_FRAMEWORK`
microservice auto-instrumented at JVM startup so that HTTP, database, and
inbound event-stream spans are captured without manual code changes to each
service.

#### Acceptance Criteria

1. EVERY `Service_Module` in `Middleware/` SHALL attach the `OBSERVABILITY_TRACING`
   auto-instrumentation agent at JVM startup via the `DevOps/Local/` compose
   configuration and the `SERVICE_BUILD_TOOL` run configuration.
2. EVERY `Service_Module` SHALL set the `OBSERVABILITY_TRACING` resource
   attribute `service.name` to the value of `spring.application.name` so that
   spans are tagged with the correct service identity in the tracing backend.
3. EVERY `Service_Module` SHALL export spans to the `OTelCollector` endpoint,
   configured as an externalized environment variable (inherited GP-Rq-11); the
   endpoint SHALL NOT be hard-coded.
4. THE auto-instrumentation SHALL capture at minimum: inbound HTTP request spans,
   outbound HTTP client spans, `RELATIONAL_STORE` query spans, `DOCUMENT_STORE`
   operation spans, `CACHE` operation spans, and `EVENT_STREAM` producer/consumer
   spans.
5. WHEN the `OTelCollector` is unreachable, THE `Service_Module` SHALL continue
   operating normally; span export failure SHALL NOT propagate as a service error
   (inherited GP-Rq-10 resilience).

---

### Requirement 2: W3C TraceContext Propagation over HTTP

**User Story:** As a platform operator, I want W3C `traceparent` and `tracestate`
headers propagated on all HTTP calls between services so that a single distributed
trace spans multiple services without gap.

#### Acceptance Criteria

1. EVERY `Service_Module` SHALL use the W3C TraceContext propagation format
   (`traceparent` / `tracestate`) for all outbound HTTP calls; it SHALL NOT
   use a proprietary header format for trace propagation.
2. WHEN a `Service_Module` receives an inbound HTTP request carrying a
   `traceparent` header, THE service SHALL continue the existing trace (adopt
   the incoming trace ID) rather than starting a new root span.
3. WHEN a `Service_Module` receives an inbound HTTP request without a
   `traceparent` header, THE service SHALL start a new root span.
4. THE `CorrelationId` (GP-Rq-2) SHALL be included as a span attribute
   `correlation.id` on every span generated by a `Service_Module`, so that
   correlation IDs and trace IDs are jointly queryable in the tracing backend.

---

### Requirement 3: Span Naming Convention

**User Story:** As a developer querying traces, I want a consistent span naming
convention so that I can filter and group spans by service, operation type, and
entity without relying on auto-generated names.

#### Acceptance Criteria

1. HTTP controller spans generated by auto-instrumentation SHALL be overridden
   to follow the convention `{service-name} {HTTP_METHOD} {route-template}`
   (e.g. `trade-lifecycle-service GET /api/v1/trades/{tradeId}/state`).
2. `EVENT_STREAM` consumer spans SHALL be named
   `{service-name} receive {topic-name}`.
3. `EVENT_STREAM` producer spans SHALL be named
   `{service-name} send {topic-name}`.
4. `RELATIONAL_STORE` spans generated by auto-instrumentation SHALL include
   the `db.operation` and `db.sql.table` attributes; span names SHALL NOT
   include literal SQL text.
5. Custom application-level spans (hand-instrumented in service code) SHALL
   follow the naming convention `{service-name}/{domain-operation}` (e.g.
   `trade-lifecycle-service/process-lifecycle-transition`).

---

### Requirement 4: Business Context Baggage

**User Story:** As a platform operator investigating a trade issue, I want
`tradeId` and `regionCode` propagated as baggage on every span in the trace
so that I can filter all spans related to a specific trade across all services.

#### Acceptance Criteria

1. WHEN a `Service_Module` handles a request or event for a specific `tradeId`,
   THE service SHALL set `tradeId` as a `Baggage` entry and as a span attribute
   `trade.id` on every span generated within that unit of work.
2. WHEN a `Service_Module` handles a request or event carrying a `regionCode`,
   THE service SHALL set `regionCode` as a `Baggage` entry and as a span
   attribute `region.code` on every span generated within that unit of work.
3. THE `Baggage` entries `tradeId` and `regionCode` SHALL be propagated to all
   downstream HTTP calls so that child services automatically inherit the
   business context.
4. `Baggage` entries SHALL NOT carry sensitive data, monetary values, PII, or
   any non-synthetic identifier; only `tradeId` (`FX-` prefixed) and
   `regionCode` (enum value) are permitted as business-context baggage.

---

### Requirement 5: Span Status and Error Tagging

**User Story:** As a developer debugging a failed request, I want error spans
tagged consistently so that I can find all failed spans for a service or trade
in a single query.

#### Acceptance Criteria

1. WHEN a `Service_Module` handles a request that results in an unhandled
   exception (a `500` response), THE outermost span SHALL be set to status
   `ERROR` with the exception class name recorded as the `error.type` attribute.
2. WHEN a `Service_Module` handles a request that results in a `4xx` client
   error, THE span status SHALL remain `OK` (client errors are not server
   errors); the HTTP status code SHALL be recorded as the `http.response.status_code`
   attribute.
3. THE span SHALL NOT record exception stack traces as span attributes (to avoid
   bloating trace storage); the stack trace belongs in the structured log entry
   correlated via the `traceId`.
4. EVERY `EVENT_STREAM` consumer span that results in the message being
   dead-lettered SHALL be set to status `ERROR` with `error.type =
   dead_lettered` and the `dlq.failure.reason` recorded as a span attribute.

---

### Requirement 6: Local Tracing Backend Configuration

**User Story:** As a developer running locally, I want traces visible in the
local tracing UI without any cloud configuration so that I can debug distributed
calls during development.

#### Acceptance Criteria

1. THE `DevOps/Local/` compose stack SHALL include an `OTelCollector` service
   and a local tracing UI, both pinned to explicit image versions (never
   `latest`).
2. EVERY `Service_Module`'s local compose configuration SHALL set the
   `OBSERVABILITY_TRACING` exporter endpoint to the local `OTelCollector`.
3. THE local tracing UI SHALL be accessible on a documented port, listed in
   `DevOps/Local/README.md`.
4. ALL trace data in local development SHALL use only `SyntheticData`
   (`FX-` prefixed `tradeId`s, fictional service names); no real trade data
   SHALL appear in local trace stores.
