# Requirements Document — OTel Kafka Tracing

> **Technology-agnostic spec.** References **Technology Roles** from
> `01-initial-setup/01-technology-stack`. Contains no product names or versions.

## Introduction

This feature defines the **W3C TraceContext propagation standard through the
`EVENT_STREAM`** so that a distributed trace spans across service-to-service
HTTP calls *and* across asynchronous event boundaries. Without this, a trace
started at trade capture breaks when the event is consumed by the Trade Lifecycle
service, making end-to-end investigation impossible.

This spec has no new business logic. It instruments event producers and consumers
built in phases 02 and 03 with the `OBSERVABILITY_TRACING` mechanism for
`EVENT_STREAM` span correlation. All identifiers in examples use the
`FX-` prefix.

---

## Glossary

- **ProducerSpan**: The `Span` created when a `Service_Module` publishes a
  message to the `EVENT_STREAM`; represents the act of sending.
- **ConsumerSpan**: The `Span` created when a `Service_Module` consumes a
  message from the `EVENT_STREAM`; represents the act of receiving and
  processing.
- **TraceHeader**: The W3C `traceparent` (and optionally `tracestate`) value
  injected into `EVENT_STREAM` message headers by the producer and extracted
  by the consumer to continue the trace.
- **LinkedSpan**: A `ConsumerSpan` that is linked (not parented) to the
  `ProducerSpan` when the consumer processes a message in a separate trace
  context (e.g. batch consumer); linking preserves the causal relationship
  without forcing all consumer work into one trace tree.
- **StreamProcessingSpan**: A `Span` generated by the `STREAM_PROCESSING`
  application (`event-sequence-processor`) for each record it processes;
  propagates context from the source record's `TraceHeader`.

## Requirements

### Requirement 1: Trace Context Injection by Producers

**User Story:** As a platform operator, I want every event published to the
`EVENT_STREAM` to carry W3C `traceparent` headers so that the producing
service's trace context can be recovered by any consumer.

#### Acceptance Criteria

1. EVERY `Service_Module` that publishes to the `EVENT_STREAM` SHALL inject
   the active W3C `traceparent` (and `tracestate` if present) as message
   headers on every published record.
2. THE `TraceHeader` injection SHALL occur automatically via the
   `OBSERVABILITY_TRACING` auto-instrumentation for `EVENT_STREAM` producers;
   no manual header-setting code SHALL be required in service logic.
3. THE `ProducerSpan` SHALL record the `EVENT_STREAM` topic name as the
   `messaging.destination.name` attribute and the `PartitionKey` (`tradeId`
   or `regionCode`) as the `messaging.kafka.message.key` attribute.
4. THE injected `traceparent` SHALL carry the `traceId` of the unit of work
   that triggered the publish (e.g. the HTTP request that led to the state
   change), not a freshly generated `traceId`.
5. WHEN a `Service_Module` publishes multiple events in one unit of work (e.g.
   during a batch operation), EACH event SHALL carry the same `traceId` but a
   distinct `spanId` reflecting its individual `ProducerSpan`.

---

### Requirement 2: Trace Context Extraction by Consumers

**User Story:** As a platform operator, I want every `EVENT_STREAM` consumer
to extract the W3C `traceparent` from the message headers and continue or link
the trace so that consumer-side spans appear in the same trace as the producer.

#### Acceptance Criteria

1. EVERY `Service_Module` that consumes from the `EVENT_STREAM` SHALL extract
   the `traceparent` header from each incoming record and use it as the parent
   context for the `ConsumerSpan`.
2. THE `TraceHeader` extraction SHALL occur automatically via the
   `OBSERVABILITY_TRACING` auto-instrumentation for `EVENT_STREAM` consumers;
   no manual header-reading code SHALL be required in service logic.
3. WHEN a message carries no `traceparent` header (e.g. a message produced
   before this instrumentation was deployed), THE consumer SHALL start a new
   root `ConsumerSpan` rather than failing.
4. THE `ConsumerSpan` SHALL record the `EVENT_STREAM` topic name, partition,
   and offset as span attributes so that the consumed message can be located
   from the trace.
5. THE `ConsumerSpan` SHALL include the `trade.id` baggage attribute
   (per `05-observability/01-otel-spring-boot` Requirement 4) extracted from
   the event envelope's `tradeId` field.

---

### Requirement 3: Producer-Consumer Span Linking

**User Story:** As a developer investigating a trade's end-to-end flow, I want
producer and consumer spans linked in the trace so that I can navigate from
the event publish to the event consumption in one query.

#### Acceptance Criteria

1. FOR synchronous consumer patterns (one record processed per poll), THE
   `ConsumerSpan` SHALL use the `ProducerSpan` as its **parent** so that
   the consumer work appears as a child of the producer in the trace tree.
2. FOR batch consumer patterns (multiple records processed in one poll), THE
   batch processing span SHALL **link** to each individual `ProducerSpan`
   rather than parent it, to avoid a wide, misleading trace tree.
3. THE `STREAM_PROCESSING` application SHALL create a `StreamProcessingSpan`
   for each record it processes, linked to the source record's `ProducerSpan`.
4. THE tracing backend SHALL surface both parent/child relationships and span
   links so that both patterns (Requirement 3.1 and 3.2) are navigable.

---

### Requirement 4: DLQ Span Tracing

**User Story:** As a developer investigating a dead-lettered message, I want
the DLQ routing decision traced so that I can see in the trace exactly when
and why a message was dead-lettered.

#### Acceptance Criteria

1. WHEN a `Service_Module` routes a message to a `DLQTopic`, THE dead-lettering
   action SHALL be recorded as a child `Span` of the `ConsumerSpan`, with span
   name `{service-name} dead-letter {origin-topic}`.
2. THE dead-letter span SHALL include as attributes: `dlq.origin.topic`,
   `dlq.origin.partition`, `dlq.origin.offset`, `dlq.failure.reason` (truncated
   to 200 characters), and `dlq.poison.flag`.
3. THE dead-letter span SHALL be set to status `ERROR`.
4. THE `TraceHeader` carried in the original message SHALL be propagated to the
   `DLQTopic` message headers so that the DLQ consumer can continue the same
   trace when it reads the dead-lettered message.

---

### Requirement 5: Stream Processing Trace Coverage

**User Story:** As a developer investigating a sequence anomaly, I want the
`event-sequence-processor`'s record processing visible in traces so that I can
correlate anomaly detection to the upstream event that triggered it.

#### Acceptance Criteria

1. THE `event-sequence-processor` SHALL create a `StreamProcessingSpan` for
   each record consumed from `fxops.trade.events`, linked to the record's
   `ProducerSpan` via the extracted `traceparent`.
2. WHEN the processor emits an `AnomalyEnvelope` to `fxops.sequence.anomalies`,
   THE publish SHALL produce a `ProducerSpan` that is a child of the
   `StreamProcessingSpan`, so the full chain (trade event → detection → anomaly
   publication) is traceable.
3. THE `StreamProcessingSpan` SHALL include `trade.id` and the detected
   `violationType` (if any) as span attributes.
