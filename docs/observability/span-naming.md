# Span Naming Conventions

This document defines the span naming standards for the FX Trade Operations Intelligence platform. All services follow these conventions to ensure consistent, queryable traces across the distributed system.

## General Format

All span names follow the pattern:

```
{service-name} {operation-type} {target}
```

Where:
- `{service-name}` is the `spring.application.name` of the service generating the span
- `{operation-type}` is the verb or action category
- `{target}` is the resource being operated on

## HTTP Controller Spans

HTTP spans generated by auto-instrumentation are named:

```
{service-name} {HTTP_METHOD} {route-template}
```

Examples:
- `trade-ingest-service POST /api/v1/trades`
- `trade-lifecycle-service GET /api/v1/trades/{tradeId}/state`
- `risk-calculation-service POST /api/v1/risk/calculate`
- `eod-processing-service POST /api/v1/eod/regions/{regionCode}/close`
- `business-calendar-service GET /api/v1/calendar/business-date`
- `state-reconciliation-service POST /api/v1/reconciliation/run`

## Kafka (Event Stream) Spans

### Producer Spans

```
{service-name} send {topic-name}
```

Examples:
- `trade-ingest-service send fxops.trade.captured`
- `trade-lifecycle-service send fxops.trade.events`
- `risk-calculation-service send fxops.risk.completed`

### Consumer Spans

```
{service-name} receive {topic-name}
```

Examples:
- `trade-lifecycle-service receive fxops.trade.captured`
- `risk-calculation-service receive fxops.trade.events`
- `eod-processing-service receive fxops.risk.completed`
- `event-sequence-processor receive fxops.trade.events`

## Database Spans

### Relational Store (PostgreSQL)

Auto-instrumentation captures database spans with:
- `db.operation` attribute (e.g., `SELECT`, `INSERT`, `UPDATE`)
- `db.sql.table` attribute (e.g., `trades`, `lifecycle_states`)
- Span names do NOT include literal SQL text

Example span names:
- `SELECT trades`
- `INSERT lifecycle_states`
- `UPDATE eod_regions`

### Document Store (MongoDB)

- `find fx_sequences`
- `insert anomaly_events`

### Cache (Redis)

- `GET trade:{tradeId}`
- `SET calendar:business-date`

## Dead Letter Queue (DLQ) Spans

```
{service-name} dead-letter {origin-topic}
```

Examples:
- `trade-lifecycle-service dead-letter fxops.trade.captured`
- `risk-calculation-service dead-letter fxops.trade.events`

## Custom Application Spans

Hand-instrumented spans for domain-specific operations follow:

```
{service-name}/{domain-operation}
```

Examples:
- `trade-lifecycle-service/process-lifecycle-transition`
- `risk-calculation-service/evaluate-risk-rules`
- `eod-processing-service/check-region-readiness`
- `business-calendar-service/resolve-business-date`
- `state-reconciliation-service/detect-state-drift`
- `event-sequence-processor/detect-sequence-violation`

## Span Attributes

### Standard Attributes (all spans)

| Attribute | Description | Example |
|-----------|-------------|---------|
| `service.name` | Service identity | `trade-lifecycle-service` |
| `correlation.id` | Request correlation ID | `corr-abc-123` |
| `trade.id` | Trade identifier (when applicable) | `FX-000001` |
| `region.code` | Region code (when applicable) | `APAC` |

### Error Attributes

| Attribute | Description | Example |
|-----------|-------------|---------|
| `error.type` | Exception class or error category | `IllegalStateException` |
| `http.response.status_code` | HTTP response code | `500` |
| `dlq.failure.reason` | Reason for dead-lettering (max 200 chars) | `Invalid state transition` |
| `dlq.origin.topic` | Original topic before DLQ | `fxops.trade.captured` |
| `dlq.origin.partition` | Original partition | `3` |
| `dlq.origin.offset` | Original offset | `12456` |
| `dlq.poison.flag` | Whether message is poison | `true` |

### Kafka-Specific Attributes

| Attribute | Description | Example |
|-----------|-------------|---------|
| `messaging.destination.name` | Kafka topic name | `fxops.trade.events` |
| `messaging.kafka.message.key` | Message partition key | `FX-000001` |
| `messaging.kafka.partition` | Partition number | `2` |
| `messaging.kafka.offset` | Message offset | `5678` |

## Span Status Rules

| Condition | Status | Notes |
|-----------|--------|-------|
| Unhandled exception (5xx) | `ERROR` | `error.type` = exception class |
| Client error (4xx) | `OK` | Status code recorded as attribute |
| Message dead-lettered | `ERROR` | `error.type` = `dead_lettered` |
| Successful completion | `OK` | Default |

## Notes

- Stack traces are NOT recorded as span attributes. They belong in the structured log entry correlated via `traceId`.
- All example identifiers use the synthetic `FX-` prefix.
- Baggage entries are limited to `tradeId` and `regionCode` only — no PII, secrets, or monetary values.
