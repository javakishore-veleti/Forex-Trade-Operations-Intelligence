# ADR-0031: Embedding Lifecycle — Generation, Storage, and Invalidation

## Status
Accepted

## Context
Embeddings are generated by Python sidecars, stored in pgvector, and queried by n8n agents via MCP tools. The lifecycle (when to generate, when to invalidate, when to re-embed) must be well-defined to prevent stale recall results.

## Decision

**Generation triggers:**
- **Incident embeddings**: generated by the `log-normalizer` sidecar when a trade incident is resolved (post-resolution, not during). The resolution summary is embedded.
- **Rule embeddings**: generated by a one-time batch job on DRL rule package deployment. When `RULE_VERSION` changes, all rules in the new package are re-embedded.

**Storage conventions:**
- Each embedding row carries: the source text (for debugging), the embedding vector, a `metadata` JSONB (source_version, generated_at, model_name, model_version), and a `created_at` timestamp
- The embedding model name and version are stored per-row so mixed-model vectors are detectable

**Invalidation rules:**
- When a new rule package deploys (new `RULE_VERSION`), old rule embeddings for superseded rules are soft-deleted (`deleted_at` timestamp set, excluded from search queries)
- Incident embeddings are never deleted (append-only historical record) but are excluded from similarity search after 90 days unless explicitly included
- If the embedding model changes, ALL existing embeddings must be regenerated in a backfill job (dimension or distance-space change makes old vectors incomparable)

**Query patterns (MCP tools):**
- `findSimilarIncidents(embedding, topK, maxAgeDays)` — cosine similarity, filtered by age
- `searchRuleCorpus(embedding, topK, ruleVersion)` — cosine similarity, filtered by active version

## Alternatives Considered
- **Eager embedding on every event** — rejected; too many embeddings, most never queried
- **Lazy embedding on first query** — rejected; adds latency to agent response
- **No versioning of embedding model** — rejected; mixing vectors from different models silently degrades recall
- **Hard delete on invalidation** — rejected; breaks audit trail and makes re-embedding harder

## Consequences
- Embeddings are generated at well-defined lifecycle points (resolution, deployment)
- Stale embeddings are excluded by filter, not deleted
- Model changes require explicit backfill (detectable via metadata)
- MCP tools query with age/version filters for relevant results
